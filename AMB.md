# Omarchy Voice — release-readiness audit and remediation plan

**Verdict: NOT READY.** Audit of `docs/usage-guide` at `453a283bb08f8f6b3087b28d544cff861a47e6ce`, 2026-10-09. No source, installation, desktop configuration, Git history, or upstream listing was changed. This is a plan, **not** authorization to publish. The checkout was clean before this report; it is one documentation commit ahead of `origin/main`. The current default branch is not the audited README revision.

## Executive assessment

The architecture has useful boundaries: deterministic intent parsing, argv-only actions, explicit permission checks, same-UID owner-only socket, bounded recording/STT, a killable transcription worker, confirmation token for window closing, and no modification of packaged Omarchy or Voxtype. The local Python tests, installed-Omarchy manifest/Lua/QML harness, and lockfile consistency check pass. These results **do not** demonstrate a fresh installation, live microphone recognition, reliable Hyprland hold/release, visible shell behavior, or safe first-use uninstall.

Three release blockers remain: transcript-log permissions are not private (the current host's 0700 home directory mitigates direct access today), the repository cannot be installed/listed as a plugin from its root, and the core voice workflow has not been acceptance-tested end-to-end for this revision. Important documentation, preflight, and activation-status issues also remain. Avoid introducing an installer or redesigning the action router just to address the listing format.

## Publication channel and requirements — provenance matters

- **Official Omarchy runtime contract (verified):** [Omarchy manual — Shell Plugins](https://omarchy.org/manual/shell-plugins/) describes root-manifest git installs, validation, enabled state, updates, removal, and the unsandboxed shell. The [Quattro shell reference](https://github.com/omacom/omarchy/blob/quattro/docs/omarchy-shell.md) and [first-party plugin reference](https://github.com/omacom/omarchy/blob/quattro/shell/plugins/README.md) are runtime references, **not** an upstream plugin-acceptance PR process. Local Omarchy `4.0.4-1` advertises `omarchy plugin add/validate/update/remove` and validates `./plugin`; local Hyprland reports `0.56.2`. This does not establish compatibility with every release.
- **Recognized listing route (verified, but community-maintained):** [omarchy.org/plugins/](https://omarchy.org/plugins/) redirects to `plugins.omarchy.org`; its [publishing guide](https://plugins.omarchy.org/publish.html) links the [community marketplace submission issue form](https://github.com/omacom/omarchy-plugin-marketplace/issues/new?template=submit-plugin.yml). The marketplace's own [AGENTS.md](https://github.com/omacom/omarchy-plugin-marketplace/blob/main/AGENTS.md) calls it independent and not affiliated with Omarchy or 37signals. Thus it is an Omarchy-site-linked community directory, **not** evidence of an Omarchy core-maintained plugin registry, official certification, or an obligation to PR `omacom/omarchy`. A separate [registry prototype](https://github.com/omacom/omarchy-plugin-registry) says its Quattro client/deployment are still required before launch; do not confuse that future protocol with the currently linked issue workflow.
- **Marketplace submission requirements (verified for that community directory):** [SUBMISSION.md](https://github.com/omacom/omarchy-plugin-marketplace/blob/main/SUBMISSION.md) specifies one public GitHub repo, root manifest/README/license, external dependency and install/removal documentation, globally unique non-`omarchy.*` ID, one category and 1–3 allowed tags, optional root preview, and five owner-confirmed checklist statements. `local.omarchy-voice` is not in the reserved `omarchy.*` namespace, but its global uniqueness was **not checked**. Reasonable candidate: `Desktop`; tags `ai`, `bar`, `hyprland` (confirm before submission). The [issue template](https://raw.githubusercontent.com/omacom/omarchy-plugin-marketplace/main/.github/ISSUE_TEMPLATE/submit-plugin.yml) requests repository URL, category, tags, maintainer notes, and ownership/configuration confirmations. `SECURITY.md` describes exact-commit static baseline and maintainer approval; `service-management`/`installer` capabilities may require review, not automatic rejection. A listing is not a security audit; installation of mutable upstream HEAD is not bound to the reviewed SHA.
- **Own recommendations, not external requirements:** security/private-log repair, live voice acceptance, clearer preflight, aligned backend/widget versions, reversible F5 instructions, and improved STT activation check are this audit's release quality gates.

**No submission was made.** Once gates pass, the owner should verify the target marketplace rules still apply, confirm the checklist/ownership, and explicitly approve the issue content before anyone submits. Publishing the repository to GitHub and listing it are separate decisions.

## Prioritized remediation with acceptance and verification

1. **Protect existing and new transcripts (B1).** Implement private log creation and safe handling of an existing 0644 file. Add automated mode/ownership and rotation tests with umask 022; manually verify permission metadata without displaying log contents. In the meantime, the repository owner should restrict the existing `voice.log` and its directory deliberately; this audit did not change them. Acceptance: neither fresh manual CLI use nor the service leaves speech readable by another UID.
2. **Package the plugin for git installation (B2).** Choose either a root-manifest source layout or a separate distributable plugin repository, update manifest paths/ID/docs atomically, and test `omarchy plugin validate .` on the exact distributable root. Acceptance: fresh public clone installs with the documented `omarchy plugin add <URL> --enable`, widget is discovered, and `update/remove` work without overwriting unrelated user config; backend/systemd/hotkey installation remains explicit and reversible.
3. **Complete clean-user acceptance (B3, I1, I5).** On a consenting disposable graphical session, use the published-candidate steps from a fresh clone, explicitly inspect existing F5 bindings and back them up, start the user service, check `doctor`, fetch the model, verify F5 press/release → local transcription → harmless action (e.g. mute with reversal or switching to a spare workspace), verify unknown speech/no-op and cancellation/timeout, then Apply a phrase and test uninstall/restore. Do not test close/lock without consent. Acceptance: record exact Omarchy/Hyprland/Python/package versions, observed status/side effects, failures, and safe cleanup. Test first-time config vs saved config separately. Document untested CUDA/other environments rather than claiming support.
4. **Make preflight and activation honest (I2, I4).** Expand dependencies and diagnostics; add tests for missing `systemd-run`, model-offline failure, restart followed by daemon failure, and STT settings mismatch. Acceptance: a green readiness message is backed by a live daemon readback and an actual safe transcription probe for the configured model; a failed probe is actionable and does not claim the setting active.
5. **Prepare a coherent release revision (I1, I3).** Remove stale/private instructions, document backend/tool/widget lifecycle on the chosen layout, align version metadata and README with implementation, then rerun checks at the exact commit intended for the public default branch. Acceptance: the same commit has current README/license/manifest, documented external dependencies and complete install/update/remove steps, an unambiguous version, and no untracked runtime artifacts; subsequent release/tag/submission requires owner approval.
